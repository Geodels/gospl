## Input-mesh contract (`domain: npdata`) + the two neighbour tables
The input `.npz` supplies `v` (coords), `c` (triangles), `z` (elevation). Two invariants are enforced or assumed at load:

**Max vertex degree is 12, everywhere.** goSPL keeps neighbours in fixed-width `(npoints, 12)` Fortran tables and there are **two different ones** — do not conflate them:

| Table | Built by | Scope | Walked by |
|---|---|---|---|
| `FVnID`/`FVnNb` (+ `FVnIDfNb`, `FVeLgt`, …) | `definetin` (per rank, on the local mesh) | **per-partition**, the FV stencil | every FV operator, `mfdreceivers`/`mfdrcvrs`, hillslope, advection |
| `FVgnID`/`FVgnNb` | `globalngbhs` (**rank 0 only**, on the whole mesh) | **global**, input-mesh ids | `epsfill` only |

`globalngbhs` now bound-checks: excess connections are dropped rather than written past the end, it returns `nover` (count of over-degree vertices), and it clamps `FVgnNb` to 12 so the table stays walkable. `_buildMesh` `bcast`s `nover` (the call is rank-0-only, so a rank-local raise would deadlock np>1) and every rank raises the same `ValueError`. **`definetin` has the same 12-slot cap and is NOT bound-checked** — if you ever need to accept higher-degree meshes, both must be widened together, plus `mfdreceivers`'s 12 flow directions. Degree is ≤8 on every mesh goSPL generates; an externally refined triangulation is the risk case.

**`epsfill` (`fortran/functions.F90`) is not a general DEM filler.** It is Barnes (2014) Priority-Flood+ε, correct, but with two properties that are load-bearing wherever it is called:
- **Seeding is `elev < sl` and nothing else** — there is no notion of a domain boundary. With no cell below the cut-off the queue is never seeded and it **silently returns the input unchanged**. That is why `seaplex._matOcean` first forces `hsmth[self.outletIDs] = BOUNDARY_FLOW_SENTINEL` on a flat model. Everything below `sl` is pre-flagged and frozen, so a closed basin dipping below the cut-off stays a sink by construction (this is also the mechanism behind the `oFill` bug fixed 2026-08-22).
- **ε is one ULP (`nearest`)**, ~1e-13 m at z≈1000 m. Fine inside the model, where the filled surface feeds `mfdrcvrs` in the same step in float64 and is then discarded. It does **NOT** survive float32: rounding a ULP-filled surface to float32 restores essentially every depression. Never persist an `epsfill` result at reduced precision.

**Pre-filling the input mesh** (an initial-condition change, not a fix — the model fills internally every step and keeps the unfilled z) is done by `scripts/fill_mesh_pits.py`: same kernel, explicit outlet seeding (`--sea-level`/`--borders`/`--outlets` × `--outlet-mode elevation|absorbing`), a degree check before it calls the Fortran, and a `--backend python --epsilon` path for a physical increment when the result is written to disk. **`--flow-accum`** writes steepest-descent upstream-cell counts (or area) for the filled surface into the output npz (`flowacc`) as a mesh QC view — deliberately SFD, not goSPL's MFD, because single threads make a bad flat pattern obvious; the topological sweep follows the same `auto`/`numba`/`python` contract as `analyse.provenance._get_sweep` (0.1 s vs 2.3 s at 11.5M cells). Guard: `test_fill_mesh_pits_flow_accumulation` (counts conserved over terminals, monotone downstream, njit == python). **`--flat-resolve`** replaces the flood-order gradient inside each filled flat with Garbrecht & Martz (away from the inflow rim, towards the outlet), because Priority-Flood+ε drains a flat along the order the flood reached each cell — the geometric-banding artefact — and **`--epsilon` cannot fix it** (measured: flow directions bit-identical over 1e-6..1e-2, fill-shape corr 1.000000; only the scale changes). Two invariants are load-bearing and were each broken once while writing it: the per-flat rise is capped at **half the smallest gap to ANY adjacent flat, both directions** (a one-sided cap lets the LOWER flat of a stacked pair climb into the cell above it), and the fill underneath must keep a **token increment, never exactly zero** (with a 0 increment a basin can come out exactly level with the ground it drains through, so the outlet direction is not recoverable from the surface and the flat stays a sink). Guard: `test_flat_resolve_is_sink_free_and_reshapes_drainage` (asserts no sinks + directions changed; it does NOT assert increased flow concentration — real on a large flat, ~73% peak-drainage gain at 610 cells, but it washes out on a small one). Size-selective: `--max-depth`/`--max-volume`/`--max-cells` leave a depression at its input elevation when it exceeds a limit (a depression = a connected component of the raised set, measured with barycentric-dual cell areas), so an artefact sweep does not also delete the genuine endorheic basins; the revert is exact and local (every other cell stays bitwise equal to the unrestricted fill). Docs: `docs/user_guide/inputfile.rst` (`_fillpits`), cross-linked from `tech_guide/dep.rst`, `tech_guide/flow.rst`, `user_guide/running.rst`.

## Dead Fortran removal

**Dead Fortran removal (2026-06).** The partition-invariance work orphaned `fill_rcvs` (flat-routing receiver pick, now Python in `_dirFlats`) and `spill_pts` (spill selection, now Python in `_pitInformation`). Removed together with eight pre-existing never-called kernels — `definegtin`, `distocean`, `donorslist`, `donorsmax`, `gfill`, `scale_volume`, `stencil`, `stratathreesed` — from both `fortran/functions.F90` and `fortran/functions.pyf`. Each was verified to have **zero invocations** in Python (`from gospl._fortran import …`) and zero internal Fortran callers before removal. **`filllabel` and `definetin` were deliberately kept** (along with everything `definetin` calls — `distance`/`euclid`/`gtriarea`/`gtriareasphere`/`slerpmidpt`/`slerpvec`/`striarea`). `filllabel` is itself uncalled/unimported (it stays in both `.F90` and `.pyf` by intent — do NOT remove it on a dead-code sweep). The priority-queue/queue infrastructure (`PQpush`/`PQpop`/`shiftdown`/`pop`/`push`/`spop`/`spush`/`ppop`/`ppush`/`wpop`/`wpush`) stays — it's used by the priority-flood and `filllabel`. **A second sweep (2026-06-24)** removed the Numerical-Recipes FFT chain `four1`/`realft`/`sinft` and the gFlex grid helper `addw` — orphaned by the gFlex/FFT-flexure + spectral-orography removals (none were in the `.pyf`, none imported, the only callers were each other), `functions.F90`-only edit. **Before removing any Fortran routine, confirm both: no `from gospl._fortran import <name>` anywhere AND no internal `call <name>`/`<name>(` in `functions.F90` — the f2py `.pyf` interface and the `.F90` body must be edited together.**

## Memory-safety lessons

- **`meshparams` module allocatables must be freed/resized per mesh in `definetin` — `faceVel` was the bug behind the orography ubuntu `SIGABRT`.** `getfacevelocity` allocates the module array `faceVel` lazily (`if(.not. allocated) allocate(faceVel(nb,12))`), and `definetin` — which deallocates+reallocates **every other** FV array for the new mesh's `nb` (`faceVec`, `FVnID`, `FVeLgt`, `FVvDist`, `FVnIDfNb`, `midFace`, `FVarea`, `FVnNb`) — **never touched `faceVel`**. So across model instantiations in one process it kept the *first* model's `nb`; a later, larger mesh (orography's `oro_hill`, 8100 nodes) then wrote `faceVel(k > nb_first)` in `getfacevelocity` → **heap overflow (a WRITE)**. ubuntu glibc aborts at the *next* `malloc` — a **wandering** `SIGABRT` (seen at `MatAXPY`, then `setPreallocationNNZ`, then `cptOrography`) with no PETSc/glibc message; **macOS silently tolerates it**, so it passed there, in isolation (oro alone sizes `faceVel` right), and in `dev` (the full slow tier only runs on `master`/`release-candidate`/tags/cron, never `dev`). Fix (`c3ee9aa`): add `faceVel` to `definetin`'s per-mesh dealloc block. **When you add a new `meshparams` allocatable, free it in `definetin` like the others** — a lazily-allocated, never-freed one silently keeps a stale size and overflows on the next larger mesh. The sibling failure mode is a *correctly sized* table written past its **second** dimension: every neighbour table is `(npoints, 12)` and an append must bound-check the slot index (this was the `globalngbhs` bug fixed 2026-09-22; see `## Input-mesh contract`). The two red-herring fixes that did NOT cure it: the `conftest` autouse `_release_petsc_after_test` teardown (`cf4c736`, wrong "resource accumulation" hypothesis — kept only as GC hygiene) and the `_buildOroMat` `axpy`→`_assembleDiffMatCSR` refactor (`faebca3`, just moved the crash to the next `malloc` — kept as a reasonable cleanup but not the cure).
- **To hunt Fortran memory bugs, rebuild the extension with gfortran bounds-checking and run the suites.** `meson configure build/<cpXXX> -Dfortran_args="-fcheck=all -fbacktrace"` then `ninja -C build/<cpXXX>`, run `pytest tests/ -s` (and `pytest benchmarks/ -m benchmark`); `-fcheck=all` turns the silent out-of-bounds (that only ubuntu's glibc/PETSc catches at runtime) into an explicit `Fortran runtime error: Index … of array … bound` with the `functions.F90` line — reproducible on macOS. Reset with `-Dfortran_args=""` + rebuild afterwards (bounds-checking is slow). This is how the `faceVel` overflow and the `fill_depressions` `ggraph(0)` below-bounds read (`n = wsh(k)+1` with `wsh(k) == -1`; now guarded `n >= 1`) were found and fixed; both suites are clean under `-fcheck=all`.

## Ghost nodes see a truncated stencil (2026-10)

`FVarea` in the `meshparams` module is the area of each LOCAL Voronoi cell as `definetin` built it on the partition's own mesh. At a ghost node on the outer edge of the halo that cell is truncated, and Python's `self.larea` is halo-synced from the owners afterwards but `FVarea` is not (`updatearea` is only called on one mesh-build branch). The same holds for anything a kernel derives from a ghost's local neighbourhood (`getrange` bounds, outflow-face counts). This is harmless while the kernel only fills rows that are dropped at assembly (ghost rows map to negative `lgmap_row` indices), and wrong the moment an OWNED row reads a ghost's derived value. `adveciioe2` did (`thetain(k,p) = 1 - thetaout(n,q)` with `n` a ghost) and now takes an owner-synced `area` argument plus synced `vmin`/`vmax`/`nbout` from Python. Face geometry between an owned node and its ghost neighbour is complete locally (both triangles on that edge contain the owned node), so `faceVel`/`FVvDist` for such a face are safe. When a kernel needs a neighbour's cell-level quantity, pass it halo-synced from Python rather than reading the module array.

## Sorting parallel arrays (2026-10)

`quicksort(array, first, last, indices)` permutes `array` and ONE index array. Any other array that was filled in the same loop (an edge length, a weight) is NOT permuted. Sort a slot-position array (`pos(p) = p`) and read every parallel array through it (`id(pos(p))`, `dst(pos(p))`), as `mfdreceivers`/`mfdrcvrs` now do; sorting `id` directly left `dst` behind and gave every SPL eroder wrong slopes for months. A cheap invariant to test after any receiver-search change: on a flat mesh, `distRcv[k, j] == |x_k - x_rcv|` for every positive-weight slot.
