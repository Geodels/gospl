## Analysis tools (`gospl.analyse`)
Post-processing subpackage (NOT part of the `Model.runProcesses` pipeline; safe to edit independently). `gospl.analyse.provenance` attributes sediment deposited in sink basins to source-rock classes (per basin + per pixel) with transport distance and a Cu-fertility layer — design + the (shipped) in-model variant in `docs/DESIGN_PROVENANCE.md`, user/tech docs in `docs/tech_guide/provenance.rst`. Standalone (reads goSPL output); does **not** run inside the model. Key facts: routes the per-step net `erodep` down the re-derived flow graph (MFD default), recycling via a per-node deposited "pile"; `GosplOutput` reassembles the **partitioned** HDF5 (one file per rank per step) onto the global input-mesh ordering by KDTree (the same `tree.query(lcoords)` map goSPL uses); the topological sweep is one Numba-`njit`-compatible kernel (`_sweep_impl`) used as both the Python reference and, via `numba`, the fast path (`method='auto'`, identical results). `numba`/`geopandas` are **optional** (`pip install "gospl[analysis]"`); the tool falls back / errors clearly without them. The package is listed in `pyproject.toml` `[tool.setuptools] packages` (it must be, or it won't install). Tests: `tests/test_provenance.py`. A sparse transport-with-loss solve was evaluated and rejected (inexact under sediment under-supply + slower) — do not re-add it. **`gospl.analyse.gridexport` point location does NOT use `matplotlib.tri`** (2026-08-22): its `TrapezoidMapTriFinder` is a general-purpose structure whose build is O(minutes) on a multi-million-triangle mesh — 158 s on a 5.9M-node / 11.8M-triangle global mesh at 0.1°, and a PERIODIC grid needs two of them (one per longitude framing), so ~320 s per step before a single field is rasterised. Replaced by a nearest-node seeded search: one `cKDTree` query (reusing the tree already built for the partition reassembly, in **3-D** for a geographic mesh so it is seam-independent and shared by both framings) plus a barycentric test over the triangles incident to that node, via a node→triangle CSR adjacency (`_node_tri_csr`, built with an UNSTABLE argsort — only the set matters — which is ~4× faster). Valid because a goSPL mesh is a near-uniform Delaunay triangulation; on an irregular mesh a sliver triangle can contain a point without touching its nearest node, so a widened `_LOCATE_FALLBACK_K`-nearest retry runs on the residual (never on the whole grid). Whole-function measurement on that mesh: **403.5 s → 41.2 s (9.8×), output bitwise identical** (elev/FA/drainage_area/basin/chi). **Raster D8 hydrology (2026-08-22):** seed detection and the D8 receiver search are per-cell independent and are now **vectorised** (they were two O(n) Python loops calling a per-cell neighbour *generator* — tens of millions of yields; 4.9 s + 11.6 s of a 28.7 s pass). The three genuinely sequential passes (priority-flood fill, area accumulation, basin/chi/flowdist — each a dependency chain along the flow network) go through `_get_d8_kernels(method)`, the same `'auto'`/`'numba'`/`'python'` contract as `provenance._get_sweep`. Result: **28.7 s → 1.52 s with numba (18.9×), → 9.43 s without (3.0×)**, bitwise identical (`filled`/`drainage_area`/`chi`/`flowdist`/`basin`/`receiver`). **There are deliberately TWO priority-flood implementations** — `_priority_flood_pyheap` (`heapq`, the reference) and `_priority_flood` (array heap, njit): `heapq` is C so it wins in pure Python, numba cannot compile it at all, and shipping only the njit-shaped one made the pass ~4× SLOWER for anyone without numba (42 s vs 28 s). Do NOT collapse them; `test_d8_flood_backends_agree` pins them together. Both vectorised loops sweep the 8 directions ONE AT A TIME keeping only `(n,)` state — materialising `(n,8)` float64 neighbour elevations/distances/slopes is ~1.7 GB of temporaries on a 6.5M-cell grid, which matters because this tool is run several steps at a time in parallel workers (the `(n,8)` neighbour table itself is `int32` for the same reason). The step-independent geometry is now reusable across steps via **`GridBuilder`** (`grid_export` is a thin wrapper over it, so there is ONE implementation and they cannot diverge): build once, `export(step)` many times — measured 42.0 s/step → 11.6 s setup + 27.2 s/step, bitwise identical, and the per-partition local→global index maps are cached too (goSPL's `topology.p*.h5` has no step index, so they are step-independent). The cache is per instance, so under process parallelism hand each worker a CHUNK of steps, not one step. Guard: `test_gridbuilder_matches_grid_export_and_caches` (pins equality against `grid_export` AND that the partition maps are lazily built and reused). Guard: `test_tri_interp_matches_matplotlib_trifinder` pins the located set AND the interpolated values against `matplotlib.tri.LinearTriInterpolator` on a randomised Delaunay.
